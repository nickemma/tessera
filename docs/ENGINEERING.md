# TESSERA — Engineering Design

**Companion to:** `RPD.md` (what and why). This document is *how*.

---

## 1. What is built vs bought

| Concern | Decision | Reasoning |
|---|---|---|
| Inference engine | **Buy — vLLM** | Continuous batching and paged attention are the state of the art and actively developed. Writing one teaches attention mechanics and serves models badly. |
| Model lifecycle, canary, scale-to-zero | **Buy — KServe** | Revisions, traffic splitting, and readiness gating already solved. Knative underneath handles scale-to-zero. |
| GPU scheduling | **Buy — K8s + NVIDIA device plugin** | Standard, and what employers actually run. |
| Autoscaling signal | **Buy — KEDA** | Scales on an external metric (queue depth). HPA on CPU is actively wrong for GPU inference. |
| Provisioning | **Buy — Terraform** | GPU node pools, spot policy, taints and tolerations as code. |
| Delivery | **Buy — Argo CD** | Git as the source of truth for what is serving. |
| **Gateway** | **Build — Go** | Nothing off-the-shelf combines OpenAI-compatible streaming, per-tenant token budgets, cost metering, and fallback routing. This is the project. |
| **Usage ledger + cost model** | **Build** | Cost attribution requires knowing your own GPU-hour rate and your own token counts. No vendor knows those. |
| **Semantic cache** | **Build (thin)** | Redis does the vector search; the tenant-namespacing and invalidation policy are ours. |

The dividing line: **anything on the token generation path is bought, anything on the tenancy and economics path is built.** That is where the unsolved problem actually is.

## 2. Why the gateway is a proxy, not a library

The gateway sits in the request path and streams tokens. Two constraints follow.

**It must add near-zero latency.** Go, no allocation per token, `io.Copy`-shaped streaming with a metering wrapper rather than parse-and-reserialize. The gateway parses the request head (for routing and budget) and the response trailer (for usage), and passes the token stream through untouched. Row 3 of the build order exists to prove this: baseline measured before the gateway, overhead measured after.

**It must not lose the usage record when a stream fails midway.** Tokens generated before a failure were still paid for in GPU time. Metering therefore happens incrementally — a counter incremented as tokens pass — flushed to the ledger on stream termination *whether or not the stream succeeded*. A ledger that only records successful requests understates cost, and understated cost is the failure mode that makes the whole project pointless.

## 3. Budgets and the fail-closed decision

Budget state lives in Redis as a token bucket per tenant per period. The check happens before dispatch.

**When Redis is unavailable, requests are rejected.** This is deliberate and worth defending, because the tempting default is to serve and reconcile later:

- Serving unmetered means a tenant can consume unbounded GPU time during a Redis outage, and the cost is real and unrecoverable.
- The failure is loud and short — Redis outages are minutes, not hours.
- "Fail open on the thing that controls spend" is how cost incidents happen.

The semantic cache, by contrast, **fails open** — a cache miss is safe, it just costs an inference. Same dependency, opposite failure policy, because the consequences differ. Both are documented in the runbook.

## 4. Semantic cache — the design and the risk

```
key   = (tenant_id, embedding(prompt))
lookup = Redis vector similarity search within tenant namespace, threshold τ
```

**The tenant is part of the key, not a filter applied afterward.** A filter is a line of code someone can remove; a namespace is structural. Cross-tenant cache leakage would mean tenant B receives text generated from tenant A's prompt — a data breach, not a bug.

**The similarity threshold τ is a correctness setting, not a tuning knob.** Set it too loose and semantically different prompts collide, returning confidently wrong answers. It ships conservative, and the hit rate at that threshold is measured rather than optimized toward. If the measured hit rate does not justify the complexity, **the cache is removed** — that outcome is acceptable and is stated up front so the decision is not defended out of sunk cost.

Cache entries carry a TTL and are invalidated on model version change, because the same prompt against a new model is a different response.

## 5. Routing and fallback

Routing inputs: requested model, tenant policy, request deadline, upstream health.

```
primary unavailable OR deadline at risk
    → eligible fallback for this tenant?
        → yes: serve, and set `model_served` + `fallback_reason` in the trailer
        → no:  fail with a typed error naming the unavailable model
```

**Silent fallback is prohibited.** A response generated by a smaller model that claims to be from the larger one produces an unreproducible quality regression that costs days to diagnose. The substitution is always reported, and `tessera_fallback_total` is a dashboard panel, not a debug log line.

Fallback eligibility is per-tenant policy — a team doing summarization may accept a smaller model; a team doing structured extraction may prefer an error.

## 6. Autoscaling on the right signal

GPU inference throughput is not CPU-correlated. A node at 100% GPU utilization may show modest CPU. Scaling on CPU produces replicas that do nothing or capacity that arrives late.

**Signal: vLLM's pending-request queue depth**, scraped by Prometheus, consumed by KEDA.

| Parameter | Consideration |
|---|---|
| Scale-up threshold | Queue depth sustained above N for M seconds — GPU pods take 60–90s to become ready, so reacting to instantaneous spikes wastes money |
| Scale-down | Long stabilization window; a cold start is expensive, thrashing is worse than one idle replica |
| Scale-to-zero | Only for models where a 60–90s cold start is acceptable; latency-sensitive models keep `minReplicas: 1` |
| Spot/preemptible | If used, preemption handling is required — a 30s termination notice must drain in-flight streams |

The cold-start number is measured in the benchmark, not assumed, because it determines which models can scale to zero.

## 7. KV cache pressure — the metric that leads

vLLM allocates a KV cache sized to available GPU memory. As it fills, vLLM preempts and recomputes sequences. **Latency degrades before throughput does**, which means:

- `tessera_kv_cache_usage_ratio` is the leading indicator of an incident
- The alert fires on cache usage, not on latency — by the time latency alerts, users have already felt it
- Admission control at a threshold (queue rather than accept) is preferable to preemption, because preemption wastes work already done

This is the single most important operational fact about running vLLM, and it belongs in the runbook's first section.

## 8. Cost model

```
cost_per_token = (gpu_hourly_rate × hours_elapsed) / tokens_served_in_period
```

Attributed per tenant by their share of tokens served. Deliberately simple, and simple is defensible:

- `gpu_hourly_rate` is what you pay — spot price, reserved rate, or amortized hardware cost. Stated explicitly in config, not hidden.
- Idle GPU time is included. A platform at 20% utilization has a high cost per token, and hiding that defeats the purpose of measuring.
- Cache hits are attributed at near-zero marginal cost, which is what makes the cache's value visible.

The break-even calculation against a hosted API uses this number and the published vendor rate at the time of measurement, with the date stated because vendor pricing moves.

## 9. Failure handling detail

| Scenario | Handling |
|---|---|
| Node preempted (spot) | Termination hook drains: stop accepting, finish or typed-error in-flight streams, deregister |
| vLLM OOM on model load | Readiness never passes; KServe holds previous revision; alert |
| Client disconnects mid-stream | Context cancellation propagates to vLLM to free the sequence — **otherwise abandoned streams consume KV cache** |
| Slow client (backpressure) | Bounded write buffer; disconnect past threshold rather than holding a GPU sequence hostage |
| Model registry unreachable | Running models unaffected; only new deploys fail |
| Usage ledger write fails | Buffer locally, retry; alert on buffer depth. Never drop a usage record silently |

The client-disconnect row is a real leak that is easy to miss: without cancellation propagation, a browser tab closing leaves a sequence occupying KV cache until generation completes.

## 10. Benchmark methodology

Published results are worthless without a stated method, so:

- **Hardware stated exactly** — GPU model, count, memory, driver version, host
- **Model stated exactly** — name, parameter count, quantization, context length
- **Load generator** — concurrency levels, prompt length distribution, output length distribution, all from a fixed seed
- **Warm-up excluded**, and stated as excluded
- **Every run reproducible** from a script in `bench/`
- **Failures published** — if throughput collapses past a concurrency level, that is the most useful graph in the report

Curves to publish: batch size vs throughput; batch size vs TTFT; concurrency vs p99; GPU utilization vs throughput; cost per million tokens vs sustained load.

## 11. Open questions

1. **GPU access** — see the RPD's closing table. Determines row 1 and whether spot preemption handling is in scope. **Blocks nothing else; a small model on modest hardware still exercises every platform concern.**
2. **Which models?** One capable model plus one small fallback is enough to prove routing. Picking specific weights early avoids designing for a hypothetical.
3. **Are there real internal consumers?** Wellspring is a candidate first tenant. A platform with a real consumer produces honest requirements; one without produces features nobody validates.
4. **Self-hosted Prometheus or managed?** Affects retention for the benchmark data, which needs to survive long enough to write the report.
